**Первым делом, до того как писать любой код:**
1. Прочитай `sql/schema.sql` и `sql/seed.sql` — это источник истины по именам таблиц и колонок. Не придумывай названия полей — используй те, что реально в схеме.
2. Прочитай `Backend/Api/index.php`, `Backend/Scripts/bootstrap.php`, `Backend/Scripts/applications.php` — пойми, что уже реализовано (роутинг, подключение к БД, существующие обработчики) и продолжай в том же стиле, не переписывая с нуля то, что уже работает.
3. Прочитай `.env` и `docker-compose.yml` — узнай, какая СУБД используется (PostgreSQL/MySQL), драйвер подключения, порт, имя контейнера с БД.
4. Если что-то в этом промпте противоречит реальной структуре БД или уже написанному коду — ориентируйся на код и БД, а меня спроси одним коротким уточняющим вопросом, не переделывай молча логику под собственные догадки.

## Что нужно сделать

Нужны PHP-эндпоинты (через существующий роутер в `Backend/Api/index.php`) для 6 страниц с динамикой. Никакой бэкенд-логики не нужно для index/about/services/delivery/privacy — они остаются чистой статикой.

### 1. `portfolio.html` — список проектов
- `GET /api/projects` — список проектов: title, slug, тип (Квартира/Дом/Коммерция), площадь, обложка, признак `is_featured`.
- Поддержать фильтр по типу через query-параметр (например `?type=apartment`), фронт уже рисует кнопки-фильтры «Все/Квартиры/Дома/Коммерция» — их нужно будет перевести с чистого HTML на JS, который дергает этот эндпоинт и перерисовывает `.project-grid`/`.project-list` без перезагрузки страницы.
- Избранный проект (`featured-project` блок) — либо тот же эндпоинт с `is_featured=true`, либо отдельный `GET /api/projects/featured`, на твоё усмотрение, лишь бы фронт не делал два разных формата ответа.

### 2. `project.html` — детальная страница проекта
- `GET /api/projects/{slug}` — один проект: title, meta (тип, площадь, стиль, год, срок), текст «О проекте», галерея изображений, 2–3 похожих проекта.
- Страница сейчас статично открывается как `project.html` без параметра — нужно читать `?slug=...` из query-строки (или сделать красивый URL через `.htaccess`, если это не усложнит остальной роутинг) и подставлять данные через `fetch()` на JS.
- Если `slug` не найден — отдать 404 и на фронте показать понятное сообщение, а не пустые блоки.

### 3. `showroom.html` — каталог товаров
- `GET /api/products` — список товаров: name, slug, категория (Мебель/Свет/Декор/Для партнеров), цена, обложка.
- Фильтр по категории через query-параметр, аналогично портфолио — кнопки-чипы уже есть в разметке, их нужно перевести на JS + fetch.
- Пагинация/«Показать еще» — either `?offset=&limit=`, либо `?page=`, главное чтобы кнопка `.load-more` дозагружала следующую порцию без перезагрузки.
- Блок «Избранная коллекция» — отдельно или как признак `collection_id`/`is_featured` в том же ответе.

### 4. `product.html` — карточка товара
- `GET /api/products/{slug}` — один товар: название, категория, цена, материал, размеры, наличие, срок, описание, массив изображений (главное + миниатюры), похожие товары.
- Текущая переключалка миниатюр (`.thumb-row button` меняет `src` у `.main-image`) должна продолжать работать, просто теперь `src` приходят из API, а не хардкодом.

### 5. `contacts.html` — **только форма**
- `POST /api/leads` с `form_type: "contact_short"`.
- Поля формы (см. разметку, id уже расставлены): `name`, `phone`, `message`. Email и тип объекта на этой форме нет — не требуй их.
- Обязательный чекбокс согласия на обработку персональных данных подразумевается текстом под кнопкой — либо добавь настоящий checkbox в форму и требуй его на бэке, либо трактуй сам факт сабмита как согласие (реши сам и укажи, что выбрал, в ответе).
- Остальной контент страницы (адрес, телефон, часы работы, карта) остаётся статичным HTML — бэкенд не трогает.
- После сабмита показать инлайн-сообщение об успехе/ошибке без перехода на другую страницу (fetch + preventDefault).

### 6. `request.html` — **только форма**
- `POST /api/leads` с `form_type: "measurement_request"`.
- Поля формы: `name`, `phone`, `email`, тип объекта (чипы «Квартира/Дом/Коммерция» — сейчас это JS-переключаемые кнопки с `aria-pressed`, значение нужно взять из выбранного чипа и отправить как отдельное поле, например `project_type`), `area` (площадь, м²), `message`.
- Секция «Как это работает» (`.process`) остаётся статичной.
- Тот же паттерн: fetch + инлайн-статус без перезагрузки.

## Технические требования

- Все SQL-запросы — через подготовленные выражения (prepared statements), никакой конкатенации пользовательского ввода в запрос.
- Валидация на бэке (не только на фронте): обязательные поля `name`+`phone` для обеих форм; `email` — формат, если передан; `area` — положительное число, если передано.
- Ответы — JSON, единый формат ошибок (например `{"error": "сообщение"}` с корректным HTTP-статусом: 400 для валидации, 404 для не найденного slug, 500 для внутренних ошибок).
- CORS — если фронт и бэк на одном домене/порту через docker-compose, скорее всего не нужен; если порты разные — добавь заголовки, но сначала проверь `docker-compose.yml`.
- Не логируй и не возвращай в ответе сырые данные из `.env` (пароли БД и т.п.).
- Внутри HTML-страниц замени статичные карточки на разметку-заглушку + `<script>` с `fetch()`, который рендерит те же CSS-классы, что уже есть в `styles.css` (`.product-card`, `.project-card`, `.related-card` и т.д.) — не изобретай новых классов, чтобы не сломать вёрстку.
